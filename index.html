    At a glance

    Three ideas run through the session: give Copilot the right context, let the repository carry your standards, and scale with agents and integrations you control.

    1

    The right context, not all the context

    Answer quality and AI-credit spend both depend on what is in the context window. One task per session, point at the right files, enable only the tools you need.

    2

    Let the repository carry the rules

    Instructions, path instructions, skills and custom agents in .github/ make short requests better - and shape code review too.

    3

    A green build is not a good change

    Copilot reviews in VS Code, Copilot CLI, GitHub pull requests and Azure Repos pull requests (generally available). People still approve.

    4

    Scale across solutions, repositories and tools

    Multi-root workspaces, extra directories in Copilot CLI, Copilot projects - and MCP for Azure DevOps, Jira and the browser, governed centrally.

    5

    Agents with a human gate

    An orchestrator delivers a story through specialist sub-agents. Humans approve before code is written and before merge; CI stays deterministic.

    Everything shown is yours to reuse

    The ClaimsDesk demo is a public GitHub template. Select Use this template → Create a new repository to make your own copy. The demo uses synthetic data and simplified rules on a .NET API and React stack.

    Getting context right

    Copilot can only use what is in its context window - so make it the right material, not everything.

    Context window
    Everything the model sees for one request - instructions, tool definitions, history, files, tool results - and the answer must fit too.
    Compaction
    Near the limit, older turns are summarised automatically. Detail is lost, so start fresh before you get there.
    AI Credits
    Since 1 June 2026 Copilot usage is billed in GitHub AI Credits based on tokens (1 credit = $0.01). Code completions are not billed.

    What fills the window - and how you control it

    Sources of context, when they are added and how to control them
    SourceWhen it is addedHow you control it
    Repository instructionsEvery requestKeep them short: a map, commands, conventions, guardrails
    Path instructions and skillsWhen matching files are involved; skill bodies only when relevantScope with applyTo; precise skill descriptions
    Tool definitions (including every MCP tool)Every request, for every enabled toolTools picker; start only the MCP servers you need; narrow agent tool lists
    Conversation historyRe-sent on every turnOne task per session; compact; hand over and start fresh
    Files, selections, search resultsWhen you attach them or the agent reads themPoint at the few files that matter
    Tool results (file reads, terminal output)As the agent worksQuiet commands and test filters

    The demo: the same model, different context

    Insufficient - one-line prompt, no repository context

    • Calculation dropped into the endpoint or mapping
    • Misses the extra £250.00 escape-of-water excess
    • No £0.00 floor; sometimes double for money
    • Few or no tests - the example claim comes out at £1,600.00

    Sufficient - story, rulebook skill, instructions, definition of done

    • Rule in the domain layer, exposed on the claim detail
    • Escape-of-water excess and the £0.00 floor applied
    • decimal money, unit and API tests for the boundaries
    • The example claim comes out right at £1,350.00

    • Run the A/B demo on a sample story: context off with a one-line prompt, then context on with a specific prompt.
    • Score it: £1,600.00 vs £1,350.00 - same model, different context.

    Managing context and tokens

    The habits that improve answers are the same ones that reduce AI-credit spend.

    1. One task, one sessionNew chat (or /clear) when the task changes. Why: every turn re-sends the history.
    2. Say what "done" looks likeGoal, files, rules, constraints, tests to add, the command to run.
    3. Point, don't paste#file, #selection, #changes; #codebase only to discover.
    4. Let the repository carry the rulesConventions in instructions, know-how in skills - not re-typed in every prompt.
    5. Keep instructions leanEvery line of the repository instructions is sent with every request.
    6. Fewer toolsEach enabled MCP tool adds its definition to every request; VS Code allows at most 128 tools per request.
    7. Quiet, targeted commandsFiltered test runs and quiet output - terminal output lands in the window.
    8. Plan, then implement freshPlan agent or /plan for big changes; implement in a new session from the plan.
    9. Compact or hand over/compact to summarise; a short handover note to restart small.
    10. Match effort to the taskLighter models or lower effort for routine edits; deeper reasoning for design and debugging.

    Project-specific standards

    Put conventions where Copilot always finds them - and keep them short.

    The Copilot customisation stack
    LayerWhereLoadedUse it for
    Deterministic checks.editorconfig, analysers, linters, CIAlways enforcedWhat must never slip
    Repository instructions.github/copilot-instructions.mdEvery requestMap, commands, conventions, guardrails, review priorities
    Path instructions.github/instructions/*.instructions.md with applyToWhen matching files are involvedLanguage or area conventions (C#, tests, React)
    Skills.github/skills/<name>/SKILL.mdOn demand; reusable task skills can be invoked by name in Copilot ChatRulebooks, procedures, templates and repeatable tasks
    Custom agents.github/agents/*.agent.mdWhen selected or called as sub-agentsRoles with limited tools, handoffs, orchestration
    Organisation and enterpriseOrganisation instructions, shared agents, managed settingsAcross repositoriesThe paved road for every team

    Writing instructions that work

    • Short and specific - a map, not a manual
    • Commands that keep output small
    • "Always / never" rules with the reason
    • What reviewers should prioritise
    • Long procedures moved into skills

    A paved road for your .NET/API and React stack

    • Make a .github/ folder like the demo's a template for new services
    • Keep organisation-wide rules in organisation custom instructions; share agents organisation-wide
    • Govern models, MCP servers and the cloud agent centrally with policies and managed settings
    • Review and version these files like code - they are code

    Code and pull request reviews

    Use Copilot to review early and often - wherever your code lives - and keep a person as the approver.

    Where Copilot code review runs
    WhereHowNotes
    VS Code - uncommitted changesSource Control view, Code ReviewCustom guidance via a setting (the demo points it at its code-review skill)
    VS Code - a branchA read-only Code Reviewer custom agentSeverity table against the house rules
    Copilot CLI/review (and /security-review)Works with any Git host
    GitHub pull requestAdd Copilot as a reviewer, or a branch ruleset for automatic reviewsEffort Lite, Balanced (default) or Max; reads repository instructions from the pull request branch
    Azure Repos pull request GARequest GitHub Copilot in Reviewers, or a branch policy for automatic reviewsInline comments and suggested changes; a human still owns approval

    What the demo review caught

    • Hard-coded excess and double for money
    • Settling a claim that was never approved
    • Claimant email written to the logs
    • Exception text returned to callers
    • Blocking calls, the system clock, no cancellation, no tests

    The change built and passed CI - every one of these would have shipped.

    Azure Repos - generally available

    • Administrators enable Copilot code review at the organisation, project and repository levels
    • Request a review from the pull request's Reviewers list, or add a branch policy to request reviews automatically
    • Set a default Lite or Balanced effort for a project or repository; choose another effort for an individual review
    • Use custom instructions and agent skills to align reviews with team standards; apply suggestions and resolve comments in the pull request
    • Usage is billed in GitHub AI Credits to the Azure subscription linked to the Azure DevOps organisation
    • Audit log events record when the feature is enabled or disabled and when its settings change

    Speaker notes

    • Planted change on branch demo/settle-claim: green build, a dozen problems.
    • Show VS Code review, then the pre-run pull request review; Azure Repos code review is generally available.

    Larger solutions and multiple repositories

    Give Copilot a map, then focus it - across one solution or several repositories.

    A map, not a manual

    A short layout table in the repository instructions tells Copilot where things live.

    Area rules where they apply

    Path instructions per language or folder; nested AGENTS.md files for large monorepos.

    Find, then focus

    #codebase to discover, then attach the few files that matter; exclude noise from search.

    Split the work

    Sub-agents each work in their own context window and return a short summary.

    Frontend and backend in separate repositories

    Options for working across repositories
    OptionHowGood for
    Multi-root workspaceOpen both repositories in one VS Code workspaceOne session reading and changing both; each keeps its own instructions
    Copilot CLIcopilot --add-dir ../other-repo or /add-dirTerminal-first work across folders
    Copilot projects previewGitHub Copilot app: give Copilot a goal across repositoriesParallel, managed agent sessions
    Copilot cloud agentCloud-sandbox sessions can span repositories in one organisationDelegated work that comes back as pull requests

    Contract first

    Agree field names and types before either side changes, make both changes in one session or coordinated tasks, and keep a contract test on each side.

    • GitHub Copilot for Jira (generally available): assign a Jira issue to the Copilot cloud agent, get a draft pull request - needs Jira Cloud and code in GitHub
    • Azure Boards (generally available): "Create a pull request with GitHub Copilot" from a work item - needs GitHub repositories connected through the GitHub app
    • Copilot code review in Azure Repos (generally available): see page 6

    Governance checklist

    • Enterprise policy "MCP servers in Copilot" decides whether MCP runs at all
    • Allow-list approved servers in enterprise managed settings
    • Prefer read-only modes and limited toolsets
    • Least-privilege tool lists in custom agents; writes behind a confirmation
    • No secrets in MCP configuration files
    • Proxy and TLS inspection allow only the approved remote endpoints

    GitHub Copilot app and Copilot projects

    Scale. The app (GA) delegates and tracks agent work in one place; projects (preview) run agent work across several repositories in parallel. Sessions continue across the app, VS Code, CLI and web.

    Automation. Recurring work such as triage and code review, with triggers, cost limits and revision history - and they learn from outcomes.

    Security fixes as tasks

    Commercials. Copilot features without a separate subscription, paying for the AI Credits used; existing customers can stay on their plans or move. Talk to your GitHub account team.

    End-to-end with agents

    One story, five specialist agents, two human decisions.

    1. Story
      Read from Azure DevOps, Jira, a GitHub issue or a local file - "Fast-track low-value claims"
    2. Analyse
      Story Analyst checks the acceptance criteria against the rulebook and finds five gaps
    3. Human gate
      A person approves the criteria before any code or test is written decision
    4. Build
      API Developer and Web Developer sub-agents work in parallel, each in its own context with only its tools
    5. Verify
      Test Engineer runs every suite, fills gaps, writes a traceability report
    6. Review
      Code Reviewer agent, then Copilot code review on the pull request
    7. Merge
      A person merges; CI runs deterministic checks only decision
    The agent team in the demo repository
    AgentToolsRole
    Feature OrchestratorDelegate, read, search, write reports, work itemsRuns the flow and the gate; never writes code
    Story AnalystRead and search onlyAcceptance-criteria quality, gap table, plan, questions
    API Developer / Web DeveloperRead, edit, run tests - each in its own areaImplement against one agreed contract
    Test EngineerRun tests, edit tests only, browserProves every criterion is covered
    Code ReviewerRead-onlySeverity-ranked review against the house rules

    AI carries the rules, humans keep the judgement

    One gate before code, tests and code written by different agents, a review before merge, and no AI in the CI critical path. The same story can also be handed to the Copilot cloud agent and come back as a pull request.

    Appendix

    Glossary, how to use the demo repository, points to confirm and the sources behind this document.

    A. Glossary

    Agent mode
    Copilot plans and makes multi-step changes, running tools and commands with your approval.
    Custom agent
    A role defined in .github/agents/*.agent.md: instructions, a limited tool list, optional sub-agents and handoffs.
    Sub-agent
    An agent called by another; it works in its own context window and returns a summary.
    Skill
    A folder with SKILL.md holding know-how or a reusable task procedure Copilot loads when relevant. This demo uses skills, not prompt files, for reusable task playbooks; invoke them by name in Copilot Chat, such as /add-endpoint.
    Path instructions
    Instructions that apply to files matching an applyTo pattern.
    MCP
    Model Context Protocol - the standard way to connect Copilot to tools such as Azure DevOps, Jira or a browser.
    Copilot cloud agent
    Formerly the Copilot coding agent: works in the cloud on an assigned task and returns a pull request.
    AI Credits
    The unit Copilot usage is billed in since 1 June 2026 (1 credit = $0.01), based on tokens.
